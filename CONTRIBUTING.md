# Contributing to BACKUPMON

We're thrilled that you're interested in contributing to BACKUPMON! This document provides a set of guidelines for contributing to BACKUPMON. These are mostly guidelines, not rules. Use your best judgment, and feel free to propose changes to this document in a pull request.

BACKUPMON is licensed under the Unlicense, a license with no conditions whatsoever which dedicates works to the public domain.

****How Can I Contribute?****
For those wishing to contribute to BACKUPMON, please make your mods to the **"backupmon.sh"** file under the "develop" branch. For more info, please see below:

------

**Reporting Bugs**
* Use a clear and descriptive title for the issue to identify the problem.
* Describe the exact steps which reproduce the problem in as much detail as possible.
* Provide specific examples screenshots or logs to demonstrate the steps

**Suggesting Enhancements**
* Use a clear and descriptive title for the issue to identify the suggestion.
* Provide a step-by-step description of the suggested enhancement in as much detail as possible.

**Your First Code Contribution**
* Pull requests are the method for submitting changes. Here's the general process:
* Fork the "develop" repository.
* Create a new branch in your fork (git checkout -b feature/my-new-feature).
* Make your changes.
* Commit your changes (git commit -am 'Add some feature').
* Push to the branch (git push origin feature/my-new-feature).
* Create a new Pull Request.

**Pull Request Guidelines**
* Write clear and concise commit messages.
* Include links to existing BUGS or REQs when possible.
* Include screenshots and logs whenever possible.
* End all files with a newline.
* Send $20 for an expedited commit turnaround <jk> :)

**Documentation Styleguide**
* Keep language simple and clear.

**Forking & Naming Your Own Version**
Forking this project is genuinely welcome, that's part of what GPLv3 is for. A few ground rules keep things clear for everyone:

* Read `TRADEMARK.md` and `NOTICE.md` before you publish a fork. The short version: modify and redistribute the code freely, but don't name your fork "BACKUPMON" or a variant of it (no "BACKUPMON ZERO," "BACKUPMON PRO," etc.).

* Pick your own name for the fork, and credit this project as the source in your README (e.g. "Based on BACKUPMON by Viktor Jaep, licensed GPLv3").

* Prefer a pull request over a parallel fork when your change is a bug fix, small feature, or something the broader user base would benefit from. It keeps one canonical, well-tested version alive instead of splintering support burden across look-alike projects.

* If you used an AI coding assistant to generate your changes, please still do the above manually, don't rely solely on the assistant to pick a compliant name or write proper attribution.

* Check the diff. (See `AGENTS.md` for the agent-facing version of this policy, which some tools will read automatically.)

* Substantial forks that add real, separate value are genuinely welcome as their own projects, this isn't about discouraging derivative work, only about keeping "BACKUPMON" pointing to one project so users aren't misled about support, security fixes, or who's behind what they're running on their router.

**More Questions?**
Questions about whether a name is far enough from "BACKUPMON"? Open a discussion before you publish — happy to give a quick yes/no. Feel free to ask for help if you need it, either via issues or through the provided contact owner @VictorJp
